## 1. 目标与非目标

**目标**

- 每个二级代理的店铺能用一个独立域名访问，页面上不出现平台主域名。
- 代理侧尽可能接近"一键"：在代理后台填一次，系统自动完成校验与生效。
- 不破坏现有支付回调、限流、后台鉴权。

**非目标**

- 不做代理自建邮件服务（当前系统根本没有邮件发送能力，见 §3.4）。
- 不做每个代理独立部署实例。所有代理共用一个应用进程和一个数据库。

## 2. 现状：一个域名今天是怎么进到应用的

```
买家域名
  → 1Panel OpenResty 的 vhost（宿主机 80/443）
  → http://<docker 网桥>:3100
  → Next.js（standalone，容器内）
```

关键事实（都已在代码中核对）：

| 事实 | 位置 | 对本需求的影响 |
|---|---|---|
| 应用只绑 docker 网桥地址，公网无法直连 | `deploy/docker-compose.yml:18`、`deploy/up.sh` | 新增域名只能在 nginx 层进，应用不需要改监听 |
| nginx 已转发 `Host $host` | `README.md:99` | **应用能拿到买家访问的真实域名**，这一层零改动 |
| 限流依赖可信代理写入的来源头 | `.env.example:9`、`KAIMI_CLIENT_IP_HEADER` | 新增 vhost 必须照抄同一套 `proxy_set_header`，否则该域名的限流失效 |
| 自带 Caddy 是可选 profile，生产未启用 | `deploy/docker-compose.yml:22-35`、`README.md:96` | Caddy 的 on-demand TLS 用不上，证书要另想办法 |
| `storefronts.domain` 列存在但**从未被任何代码读取** | `schema.ts:118`、`migrate-lib.ts:93` | 死字段。不要复用它，它属于 storefronts（平台站点）而不是 agents |
| `agents` 表没有任何域名字段 | `schema.ts:46-68` | 需要新增存储 |
| 没有 `middleware.ts` | 全仓无此文件 | host → 代理的解析层需要从零加 |
| 全站只认一个全局 base | `lib/public-url.ts:24-35` | 支付回调与店铺链接的核心约束，见 §3.2 |

### 2.1 `getPublicBaseUrl` 的取值顺序

```24:35:apps/web/src/lib/public-url.ts
export async function getPublicBaseUrl(req?: Request) {
  const candidates = [
    await getSetting("public_base_url"),
    process.env.KAIMI_PUBLIC_BASE_URL || "",
    req ? originFromRequest(req) : "",
  ];
```

生产上第一项（后台「即时发卡」里填的公网地址）已有值，所以**请求 host 永远轮不到**。这是有意的设计：易支付回调必须落在一个固定、可信、证书稳定的域名上。

## 3. 必须解决的四个问题

### 3.1 host → 代理的解析

新增 `middleware.ts`：请求 host 不是主域名时，查「域名 → agentId/slug」映射，把 `/` 重写到 `/s/{slug}`。

要点：

- 映射必须**带缓存**。middleware 跑在每个请求上，不能每次查 SQLite。用进程内 Map + 短 TTL（如 60s），配置变更时主动失效。
- 未知域名要有明确行为。建议 404 一个说明页而不是静默回主站首页，否则一个配错的域名会让买家以为进了平台官网。
- middleware 在 Node runtime 下才能访问 `@libsql/client`。Next middleware 默认 edge runtime，**这里需要确认能否用 Node runtime**，否则解析层要退化成「一个内存快照 + 定时从 API 刷新」的形式。这是本方案唯一的技术未知点，需要先做验证。

### 3.2 支付回调与回跳（最容易踩的坑）

```121:159:apps/web/src/lib/store-orders.ts
  const base = await requirePublicBaseUrl(input.request);
  // ...
    notifyUrl: `${base}/api/webhooks/epay`,
    returnUrl: `${base}/shop/order/${orderNo}?qt=${encodeURIComponent(queryToken)}`,
```

两者共用一个 `base`。必须**拆开**：

| 用途 | 域名 | 理由 |
|---|---|---|
| `notifyUrl`（服务端异步通知） | **永远主域名** | 易支付侧配置固定；且回调可用性不能压在代理自己的域名和证书上——代理域名过期，历史订单的发货会一起挂 |
| `returnUrl`（买家付完款的浏览器回跳） | **代理域名** | 否则买家付完钱被弹到一个陌生域名，看起来像被钓鱼 |
| `rechargeUrl`（买家拿到卡密后去兑换的链接） | **代理域名** | 见 §3.4，这是白牌完整性最大的缺口 |

回跳到代理域名意味着 `/shop/order/[no]` 这个路由也必须在代理域名下可访问。同理需要放行的还有 `/api/public/store-orders*`（下单与查单）。

`rechargeUrl` 是第三处、也最容易被漏掉的一处：

```35:40:apps/web/src/app/api/public/store-orders/[orderNo]/route.ts
  const origin = await getPublicBaseUrl(req);
  // ...
      rechargeUrl: origin ? `${origin}${rechargePath}` : rechargePath,
```

订单结果页给买家的兑换链接同样用全局 base 拼的。

### 3.3 后台与会话隔离

`kaimi_session` cookie 是按 host 隔离的，代理在自己域名下登录会拿到另一套会话。这本身无害，但会造成两个问题：

- 代理域名下暴露 `/admin` 登录入口 —— 增加攻击面，也让代理域名看起来像平台后台。
- 代理在自己域名登录后，改的配置在主域名下看不到「已登录」状态，容易困惑。

**建议**：middleware 在自定义域名上直接挡掉 `/admin`、`/agent`、`/login`、`/setup`，只放行店铺与公开 API。后台统一只在主域名开放。

### 3.4 白牌到底要做多深（比证书更需要先想清楚）

代理店铺本身只是买家旅程的第一站。完整旅程是：

```
店铺页 → 支付 → 订单结果页（拿卡密）→ 兑换页（把卡密换成账号）
```

后两站目前都是**平台级共享页面**，不属于任何代理：

| 页面 | 现状 | 代理域名下要不要跟着走 |
|---|---|---|
| `/s/[slug]` | 按 slug 查代理 | **必须**，这是门面 |
| `/shop/order/[no]` | 按 orderNo 查，URL 里没有 slug | **必须**，否则支付回跳就出戏 |
| `/api/public/store-orders*` | 下单与查单 | **必须**，否则店铺页的按钮全废 |
| `/recharge` | 读 `storefronts(kind=recharge)`，全站一套外观 | **建议**，否则买家最后一步被弹到平台域名 |
| `/cdk`、`/lookup` | 与代理无关 | 可选 |
| `/agent/*`、`/admin`、`/login` | 后台 | **明确挡掉**，见 §3.3 |

注意 `/recharge` 的外观来自 `storefronts` 表而不是 `agent_storefronts`，也就是说**即使让它在代理域名下可访问，页面上显示的仍是平台品牌**。要做到真白牌，兑换页需要能感知当前代理并套用代理的装修配置，这是一块独立的工作量，不在"绑个域名"的直觉预算里。

另外代理后台「兑换卡密」按钮指向的是全站配置 `agent_redeem_url`（`lib/agent-redeem.ts`），也是平台级的。

**建议**：第一版只把前三项做进代理域名，`/recharge` 显式跳回主域名并接受这个瑕疵。等确认代理真的在意，再单独立项做兑换页的多租户化。

### 3.5 顺带发现的既有问题：没有邮件发送

全仓不存在任何邮件发送设施（无 SMTP / nodemailer / Resend）。`customerEmail` 只被写入 `store_orders` 并供 `listStoreOrdersByEmail` 查单使用。买家拿卡密的唯一途径是**订单页 + `qt` token**，以及事后用邮箱查单。

这与「独立域名」无直接关系，但如果将来要做邮件发货，发件域名（SPF/DKIM/DMARC）会是另一套完全独立的域名工程，**不要和本方案混在一起估工作量**。

（本轮已顺手修掉店铺文案里"卡密秒发到邮箱"这类与实现不符的承诺。）

## 4. 两种域名形态

这是本文最重要的区分。用户想要的"一键"，只有第一种能真正做到。

### 形态 A：平台泛域名子域 `abc.你的域名`

- 一张 `*.你的域名` 的 DNS-01 泛域名证书，nginx 配一次，之后**永久不用再动**。
- DNS 只需一条 `*.你的域名` 的 A 记录，指向服务器。
- 代理**零操作、零等待、零成本**：后台填一个前缀，保存即生效。
- 真正意义上的"一键"。

代价：域名里仍带平台主域名，代理无法完全去平台化品牌。

### 形态 B：代理自带域名 `shop.他的域名`

- 代理**必须**自己去 DNS 加记录，这一步谁也替不了，所以**不存在真正的零操作一键**。
- 能做到的最好体验：填域名 → 页面直接给出要加的那条记录 → 后台轮询自动检测 → 生效后自动签证书并点亮。
- 每个域名都要独立证书 + nginx reload，这是全部运维复杂度的来源。

## 5. 证书方案对比（形态 B 的核心决策）

nginx 没有 Caddy 那样的 on-demand TLS，动态增删域名的证书必须自己解决。

### 方案 1：Cloudflare for SaaS（自定义主机名）

代理把域名 CNAME 到你提供的一个回源主机名，Cloudflare 负责为该主机名签发和续期证书，你的服务器只需要一张自己的证书。

| 维度 | 评估 |
|---|---|
| 服务器改动 | **零**。nginx 不用为每个代理域名加 vhost |
| 新增域名耗时 | 秒级（调 CF API 添加 custom hostname） |
| 续期运维 | CF 全托管，**不需要关心** |
| 失败模式 | 依赖 CF 可用性；CF 到你源站这一跳需要正确配置，否则会出现 CF 侧 5xx |
| 成本 | **按自定义主机名计费，有免费额度**。具体额度与单价请按当前官方价目核对，不要照抄旧文档 |
| 锁定风险 | 中等。迁走需要让所有代理改 DNS |
| 适合 | 代理数量会长到几十个以上、不想碰服务器证书运维 |

### 方案 2：OpenResty + `lua-resty-auto-ssl`（按需自动签发）

给 nginx 装上 Caddy 那种能力：首次收到某域名的 TLS 握手时现场签一张证书并缓存。

| 维度 | 评估 |
|---|---|
| 服务器改动 | **大**。要装 lua 模块、配 `ssl_certificate_by_lua`、给 auto-ssl 一个共享存储 |
| 新增域名耗时 | 代理 DNS 生效后**自动**，无需任何人操作 |
| 续期运维 | 自动 |
| 失败模式 | **首次握手会慢**（要现场签发），且必须实现 `allow_domain` 回调查你的数据库，否则任何人把域名指过来都会消耗你的 Let's Encrypt 签发配额 |
| 成本 | 免费 |
| 锁定风险 | 低 |
| **主要风险** | 你的 OpenResty 是 **1Panel 托管**的。手改它的配置，1Panel 升级或在面板里改动站点时可能被覆盖或冲突。这是本方案最现实的隐患 |
| 适合 | 愿意自己维护网关、不想付费、代理数量中等 |

### 方案 3：自动化 certbot + nginx reload

写一个 job：发现新的已验证域名 → `certbot certonly` → 生成 vhost → `nginx -s reload`。

| 维度 | 评估 |
|---|---|
| 服务器改动 | 中。需要一套配置模板 + reload 通道 |
| 新增域名耗时 | 取决于 job 周期，通常分钟级 |
| 续期运维 | certbot 定时任务可自动，但 reload 也要跟着自动 |
| 失败模式 | **提权面**：应用需要有权写 nginx 配置目录并触发 reload。应用一旦被打穿，等于网关被打穿。必须把这个动作隔离到一个独立的、只做这件事的小服务，不能让 Next 进程直接 `exec nginx -s reload` |
| 另一个坑 | 同样会和 1Panel 托管的配置打架 |
| 成本 | 免费 |
| 适合 | 有独立的、非 1Panel 托管的 nginx |

### 方案 4：先手动

代理提交域名 → 后台显示待处理列表 → 你在 1Panel 里加站点和证书 → 回后台点「已生效」。

| 维度 | 评估 |
|---|---|
| 开发量 | **最小**。只需要数据模型 + 校验 + middleware，不碰任何证书自动化 |
| 运维 | 每个域名一次人工，续期靠 1Panel 自动 |
| 适合 | **代理数量少（个位数到十几个）时这是性价比最高的选择** |

### 推荐

1. **形态 A（泛域名子域）无论如何都先做**。它能覆盖绝大多数代理的实际需求，开发量小，运维成本几乎为零，而且不需要在证书方案上做任何决策。
2. 形态 B 的第一版走**方案 4（手动）**，把数据模型、归属校验、middleware、returnUrl 拆分这些真正的产品逻辑先跑通并验证需求真实性。
3. 等自带域名的代理数量涨到人工受不了，再按「愿不愿意付费」在方案 1 和方案 2 之间二选一。此时前面的产品逻辑完全可以复用，只是把「人工点已生效」换成自动。

这个顺序的好处：**把不可逆的基础设施决策推迟到有真实数据之后**，前期投入不会浪费。

## 6. 数据模型

在 `agent_storefronts` 上扩展（该表已在上一期建好，一个代理一行）：

| 列 | 类型 | 说明 |
|---|---|---|
| `subdomain` | text | 形态 A 的前缀。全局唯一，需要保留字黑名单（www/api/admin/app/mail…） |
| `custom_domain` | text | 形态 B 的完整域名，小写、去端口、去尾点后存储。全局唯一 |
| `domain_status` | text | `none` / `pending_dns` / `verified` / `active` / `failed` / `disabled` |
| `domain_verify_token` | text | 随机 token，用于 TXT 校验 |
| `domain_checked_at` | text | 上次校验时间 |
| `domain_error` | text | 失败原因，直接展示给代理 |

**不要复用 `storefronts.domain`**：那张表是平台站点（shop/recharge）的外观配置，与代理是多对一还是一对一都不成立，语义会打架。那个死字段建议单独清理。

唯一性必须在 DB 上加唯一索引，不能只靠应用层查重——两个代理同时提交同一域名会穿过应用层检查。

## 7. 归属校验流程

必须有，否则代理可以填 `taobao.com`，把平台变成钓鱼站的帮凶。

```
代理填域名 shop.his.com
  → 生成 token，状态 pending_dns
  → 页面展示：请添加 TXT 记录
       _kaimi-verify.shop.his.com  →  <token>
  → 后台 job 定时解析该 TXT
  → 命中 → verified
  → 证书就绪（手动或自动）→ active
```

要点：

- 校验用 **TXT** 而不是「能访问就算」。后者在 CNAME 到你这里之后，任何人都能通过校验。
- `verified` 之后仍要**周期性复查**。域名过期或被转走后必须能自动降级到 `failed`，否则会一直给一个已经不属于该代理的域名提供服务。
- 提交频率要限流，DNS 解析是外部依赖。

## 8. 代理端交互（一键的边界）

在已有的 `/agent/storefront`（店铺装修）页加一块「店铺域名」：

- **平台子域**：一个输入框 + 实时查重，保存即生效。这是真一键。
- **自带域名**：填域名 → 立刻显示要加的 TXT 记录（带一键复制）→ 状态徽章（待添加记录 / 校验中 / 已生效 / 失败原因）→ 自动轮询，不需要代理手动点刷新。

必须明确告知代理的两件事：DNS 生效有延迟（最长可能几小时，不是系统故障）；以及域名到期会导致店铺立刻打不开，续费是他自己的责任。

## 9. 生效后需要跟着改的地方

现有生成店铺链接的位置全部要改成「优先用自定义域名」：

| 位置 | 当前 |
|---|---|
| `components/agent-dashboard.tsx:349,429,433,435` | `${origin}/s/${savedSlug}` |
| `components/agent-guide.tsx:18` | `${origin}/s/${slug}` |
| `app/agent/storefront/page.tsx:47` | `/s/${currentSlug}` |
| `components/admin-agents.tsx:592` | `/s/${agent.currentSlug}` |

建议抽一个 `agentShopUrl(agent, storefront)` 统一出口，避免以后再漏。

另外 `/s/[slug]` 路径**要继续可用**（老链接不能断），但在自定义域名生效后应输出 `rel=canonical` 指向自定义域名，避免同一店铺两个地址被搜索引擎当重复内容。

## 11. 开放问题

1. 主域名是哪个、泛域名证书用哪家 DNS 做 DNS-01？（要 API 支持自动续期）
2. 自带域名要不要作为付费功能 / 限定等级代理？这会影响是否值得投入方案 1 的成本。
3. 代理域名下是否允许他登录自己的代理后台？（我倾向不允许，只在主域名开放，见 §3.3）
4. 域名到期导致店铺打不开时，平台要不要自动把流量降级回 `/s/{slug}`？还是就让它挂着以免掩盖问题？
