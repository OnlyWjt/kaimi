# 店铺邀请返券（详细设计）

> 状态：§13 已全部确认（2026-10-13），待实现。分支 `feat/store-referral-coupons`。
> 日期：2026-10-13
> 相关代码：`lib/coupons.ts`、`lib/coupon-core.ts`（现有店铺优惠券）、`lib/store-orders.ts`（下单）、`lib/fulfillment/fulfill-store-order.ts`（发货）

---

## 0. 一句话

代理店铺的买家（邀请人）把自己的邀请链接发给别人；被邀请人在这家店**第一次**付款、发货成功，并且过了冷静期，邀请人就得到一张这家店的**邀请券**。邀请人以后在这家店下单时，输入券码使用。

- 只奖励邀请人。被邀请人这次不拿券。
- 券只能在发券的那家店用。让利从代理收益里出，平台成本、毛利不变。
- 每个商品能减多少由代理**逐个商品设置**，并且永远不会让这一单低于代理成本。

---

## 1. 角色和名词

| 名词 | 含义 |
|---|---|
| 邀请人 | 在这家店付过款、发货成功的买家，用**下单邮箱**识别（买家没有账号） |
| 邀请码 | 每个（店铺，邀请人邮箱）一个，6 位，公开的，写在邀请链接里 |
| 邀请链接 | `https://<店铺地址>/s/<slug>?ref=<邀请码>` |
| 被邀请人 | 通过邀请链接（或手填邀请码）在这家店第一次下单的人 |
| 邀请记录 | 被邀请人的一笔首单，从「冷静期中」到「已发券 / 已作废」 |
| 邀请券 | 发给邀请人的券，独立的码，只能用一次，只能用在邀请人自己的邮箱下单 |

## 2. 完整流程（例子：小王邀请小李）

```
① 小王在「gpt代充站」买了 Plus，付款、发货成功
   → 系统给「gpt代充站 + 小王邮箱」生成邀请码 K7M2QX
   → 付款成功页、发货邮件、查单页都出现「邀请好友」卡片和链接

② 小王把 https://.../s/onlywjt?ref=K7M2QX 发给小李
   → 小李打开，店铺在小李浏览器里记住 K7M2QX（30 天）
   → 小李下单时自动带上；没点链接也可以在结账页手填邀请码

③ 小李第一次在这家店付款、发货成功
   → 系统检查是否有效邀请（§4），有效就记一条邀请记录：冷静期中，7 天后到期

④ 7 天内小李这单退款 / 拒付 → 邀请记录作废，不发券
   7 天后订单仍正常 → 给小王发一张邀请券，码 ZQ8N4T7P2K，30 天有效
   → 发邮件通知小王（平台邮件开着时）；小王的查单页「我的优惠券」里也能看到

⑤ 小王下次在这家店买 Pro
   → 结账页填自己的邮箱，优惠券框里输入 ZQ8N4T7P2K
   → 按代理给 Pro 设的金额立减（§5），邮箱不是小王的就拒绝
```

## 3. 邀请码：怎么生成、怎么拿到

**什么时候生成**：这个邮箱在这家店第一次有订单**发货成功**时自动生成，不用申请。同一个邮箱在同一家店只有一个邀请码，再买也不变。换一家店就是另一个码。

**上线前的老买家**：不补。只有上线后发货成功的订单才生成邀请码；老买家要等上线后在这家店再买一单才有。上线前的订单查单页不显示邀请卡片。

判断「上线后」用这家店开启活动的时间：订单的发货时间早于代理第一次开启邀请有礼的时间，就不生成。这样代理晚些才开也一样，开之前的订单不算。`agent_referral_settings` 记 `first_enabled_at`。

**买家在哪看到**：

| 位置 | 内容 |
|---|---|
| 付款成功页（拿卡密的页面） | 「邀请好友」卡片：链接、复制按钮、规则一句话 |
| 发货邮件 | 末尾同样的链接和规则 |
| 查单页 | 同上；再加「我的优惠券」列表（§7） |

规则一句话由代理的设置自动生成，例如：「好友第一次在本店下单并满 7 天，你得一张邀请券：Plus 立减 ¥10、Pro 立减 ¥50」。

**邀请码格式**：6 位，字母表去掉易混字符（`0 O 1 I L`），按店铺唯一。邀请码本身是公开的，泄露也没关系，只是让别人成为你的被邀请人。

## 4. 什么算有效邀请

被邀请人的订单发货成功时检查，全部满足才记邀请记录：

1. 这家店的邀请返券是开着的。
2. 订单带了邀请码，并且是**这家店**的邀请码（别家店的码忽略）。
3. 被邀请人邮箱在**这家店**从没有过付款成功的订单（未付款、已关闭不算）。
4. 被邀请人邮箱 ≠ 邀请人邮箱（都先归一化，见 §9.1）。
5. 这个被邀请人邮箱在这家店以前没被算过邀请（每个邮箱每家店只算一次）。
6. 订单实付 ≥ 代理设的「好友订单最低金额」。
7. 订单不是测试 / 沙箱订单，不是管理员手动补录的单。
8. 邀请人本月（北京时间自然月）已发券数没到上限。到了也记邀请记录，状态为「超出上限」，不发券，代理能看到。

不满足的不记录，也不提示被邀请人，免得被试探规则。

## 5. 邀请券的面额：逐个商品设置

### 5.1 为什么按商品

各商品售价、成本差很多：Plus 售价 ¥150、成本 ¥121，减 ¥50 就亏了；Pro 售价 ¥1155，减 ¥50 毫无压力。一个统一的面额要么对便宜商品太狠，要么对贵商品没吸引力。

### 5.2 怎么设

代理在「邀请有礼」里给每个在售商品填**立减金额**（只做立减，不做折扣和满减；一单一种商品，立减最直观，也最好控成本）：

```text
商品                 售价       你的成本   通道费≈   最多能减   邀请券立减
Plus（菲区）         ¥150.00    ¥118.00    ¥0.90     ¥31.10     [ 10.00 ]
Plus（智利区）       ¥160.00    ¥125.00    ¥0.96     ¥34.04     [ 10.00 ]
Pro                  ¥1155.00   ¥980.00    ¥6.93     ¥168.07    [ 50.00 ]
GPT 成品号           ¥35.00     ¥30.00     ¥0.21     ¥4.79      [      ]  ← 空 = 不能用券
```

- 按 plan_key 设（地区变体分开设，因为成本不同），界面按商品分组显示。
- 只列这家店现在在卖的商品：管理员关掉的、代理自己下架的（`agent_plan_prices.agent_hidden`，另一个分支在做）不显示。已经填过金额的商品下架后，金额保留，重新上架就恢复。
- 「最多能减」= 让这一单代理收益刚好不为负的立减额（售价 − 成本 − 按通道费率算的手续费）。两个支付通道费率不同时取较大的那个。
- **填的数超过「最多能减」不让保存**。
- 空 = 这个商品不能用邀请券。至少要有一个商品填了金额才能开启。

### 5.3 券上记的是什么

发券时把当时的「商品 → 立减金额」整张表**存进券里（快照）**。代理以后改设置，不影响已经发出去的券；买家看到的面额也不会突然变。

买家看到的券：

```text
邀请券  ZQ8N4T7P2K                               2026-11-12 前有效
Plus 立减 ¥10.00 · Pro 立减 ¥50.00
```

### 5.4 结账时怎么算

1. 券码存在、属于这家店、状态「未使用」、没过期。
2. 下单邮箱归一化后 = 券的主人。
3. 当前商品在券的快照里有金额。
4. 实际减免 = min(快照金额, 当前「最多能减」)。售价或成本在发券后变了，自动封底，不会让代理亏；算出来 ≤ 0 就提示「这张券暂时不能用在这个商品上」。
5. 多件购买只减一次（按订单，不按件）。
6. 一单只能用一张券（邀请券和代理手建的券不能同时用）。

## 6. 邀请券的生命周期

```
          发券
            ↓
        [未使用] ──过期──→ [已过期]
          │  ↑
     下单锁券 │ 关单 / 未付款超时 / 退款（券未过期时）
          ↓  │
        [已锁定] ──付款成功──→ [已使用]
            
  任何未使用的券 ──代理/管理员停用、触发它的好友订单退款──→ [已停用]
```

| 事件 | 处理 |
|---|---|
| 下单 | 条件更新「未使用 → 已锁定」，并记订单 id；并发两单用同一张券只有一单成功 |
| 订单关闭 / 超时未付 | 「已锁定 → 未使用」 |
| 付款成功 | 「已锁定 → 已使用」，记实际减免 |
| 用券的那单后来退款 | 券还在有效期内就退回「未使用」，过期了就「已过期」 |
| 触发券的好友订单退款 / 拒付 | 券还没用就「已停用」；已经用了不追回，邀请记录标记「已发券后退款」，代理能看到 |
| 到期 | 定时任务改「已过期」（结账时也会实时判断） |

## 7. 买家端界面

### 7.1 付款成功页、查单页的邀请卡片

```text
┌ 邀请好友，得邀请券 ───────────────────────────────┐
│ 好友第一次在本店下单并满 7 天，你得一张邀请券：      │
│ Plus 立减 ¥10、Pro 立减 ¥50（30 天有效）            │
│ https://xxx/s/onlywjt?ref=K7M2QX          [ 复制 ] │
│ 已邀请成功 2 人 · 待到账 1 张                       │
└──────────────────────────────────────────────────┘
```

店铺没开邀请返券时不显示。

### 7.2 查单页「我的优惠券」

列出这个邮箱在这家店的邀请券：券码、各商品面额、有效期、状态（未使用 / 已使用 / 已过期 / 已停用）。查单页本来要完整订单号或邮件里的链接才能进，别人进不来。

### 7.3 结账页

- 带邀请码进来时显示一行小字「由好友邀请」，不显示邀请人是谁。
- 没带码时，在优惠券框下面有个收起的「有好友邀请码？」，展开可以手填。
- 优惠券框不变：输入邀请券码后显示「邀请券 立减 ¥10.00」，下面写明「仅限 j***@qq.com 使用」（打码），邮箱不对时提示「这张券只能用发券的邮箱下单」。

### 7.4 邮件

- 发货邮件末尾：邀请卡片（同 7.1）。
- 新邮件「你获得了一张邀请券」：券码、面额、有效期、店铺链接。
- 平台邮件没开或代理关了发货邮件时不发，买家仍能在查单页看到。

## 8. 代理端和管理端

### 8.1 代理后台「售价与优惠」→「邀请有礼」

**设置**

```text
邀请有礼                                                 [ 已开启 ]

邀请券立减（按商品）        → §5.2 的表格
邀请券有效期                [30] 天
冷静期                      [7] 天    好友订单付款后满这么多天才发券
好友订单最低实付            ¥[50]
每位邀请人每月最多得券      [10] 张

成本提示：触发一张券的好友订单你至少赚 ¥28.95；一张券用掉最多让利 ¥50.00
```

关闭后：新的邀请不再记录、链接不再显示；已经在冷静期的照常发券；已发出的券到期前照常能用。代理可以手动停用某张券。

**我的买家邀请**（列表，可按邮箱、券码搜索）

| 邀请人邮箱 | 邀请码 | 成功邀请 | 冷静期中 | 已发券 | 已用 | 让利合计 |
|---|---|---|---|---|---|---|

点开一个邀请人：
- 邀请记录：被邀请人邮箱、订单号、金额、状态（冷静期中 / 已发券 / 超出上限 / 已作废，带原因）、到期时间。
- 邀请券：券码、面额、发券时间、有效期、状态、用在哪一单、实际减免；未使用的可以「停用」（需填原因）。

**汇总**（本月 / 全部）：带来新客数、新客成交金额、发券数、用券数、让利金额、过期未用数。

代理能看到完整的买家邮箱（订单页本来就能看到）。

### 8.2 管理后台「代理」→「邀请返券」

- 全站汇总：开启的代理数、本月发券、用券、让利、带来的新客成交额。
- 按代理列表：开关状态、上面这些数；点进去看到和代理一样的明细。
- 管理员可以：替代理关闭邀请返券、停用某张券（都写审计日志）。不能改代理的面额设置。
- 异常提醒列表：同一邀请人本月触顶、短时间大量邀请、被邀请订单退款率高的邀请人，供人工查看。

### 8.3 订单和账本

- 订单详情显示「邀请券 ZQ8N… 立减 ¥10.00」，以及「由 K7M2QX 邀请」。
- 让利就是订单上的优惠减免，代理收益照常按实付算，账本、对账不需要改。

## 9. 安全和防刷

### 9.1 邮箱归一化

用于判断「是不是同一个人」和「券是不是本人用」：全部转小写、去空格；`gmail.com` / `googlemail.com` 去掉 `@` 前的点和 `+` 之后的部分。保存的是归一化邮箱的 hash；需要发邮件、给代理看的地方另存加密原文。

### 9.2 为什么必须要券码

下单邮箱不验证，谁都能填别人的邮箱。所以不能「输入邮箱就自动用券」，必须同时有：
- 券码：只发到邀请人邮箱、只显示在他自己的查单页；
- 邀请人的下单邮箱。

券码 10 位（约 50 位熵），猜不出来。结账校验券码按 IP 限流（同一 IP 每 10 分钟 20 次失败就锁 30 分钟），复用登录限流的做法。

### 9.3 刷券的成本

一个人用两个邮箱自己邀请自己是挡不住的。所以设计成**刷了也不亏**：
- 每张券都要先有一笔真付款、并过了冷静期的新客订单；
- 代理设的立减金额不超过商品利润，而且结账时实时封底；
- 设置页直接给代理看「触发一单至少赚多少、一张券最多让多少」，只要前者 ≥ 后者，被刷也是赚的；
- 每人每月上限、最低订单金额再兜底。

### 9.4 其他

- 邀请码只在发货成功后生成，没付过钱的人拿不到可以传播的码。
- 被邀请人不知道邀请人是谁；邀请卡片上只显示数量，不显示被邀请人的邮箱。
- 所有停用、关闭、设置修改都写审计日志。

## 10. 数据

### 10.1 新表

```sql
-- 每个代理一行
agent_referral_settings (
  agent_id               INTEGER PRIMARY KEY,
  enabled                INTEGER NOT NULL DEFAULT 0,
  first_enabled_at       TEXT,                    -- 第一次开启的时间，之前发货的订单不生成邀请码（§3）
  coupon_valid_days      INTEGER NOT NULL DEFAULT 30,
  cooling_days           INTEGER NOT NULL DEFAULT 7,
  min_order_cents        INTEGER NOT NULL DEFAULT 0,
  monthly_cap            INTEGER NOT NULL DEFAULT 10,
  updated_at             TEXT NOT NULL
)

-- 每个商品能减多少；没有行 = 这个商品不能用邀请券
agent_referral_plan_rewards (
  id            INTEGER PRIMARY KEY,
  agent_id      INTEGER NOT NULL,
  plan_key      TEXT NOT NULL,
  amount_cents  INTEGER NOT NULL,      -- > 0
  updated_at    TEXT NOT NULL,
  UNIQUE (agent_id, plan_key)
)

-- 邀请码：一个（店铺，邀请人邮箱）一个
agent_referral_codes (
  id                       INTEGER PRIMARY KEY,
  agent_id                 INTEGER NOT NULL,
  code                     TEXT NOT NULL,
  owner_email_hash         TEXT NOT NULL,   -- 归一化后
  owner_email_encrypted    TEXT NOT NULL,
  first_order_id           INTEGER NOT NULL,
  created_at               TEXT NOT NULL,
  UNIQUE (agent_id, code),
  UNIQUE (agent_id, owner_email_hash)
)

-- 邀请记录：被邀请人的一笔首单
agent_referrals (
  id                       INTEGER PRIMARY KEY,
  agent_id                 INTEGER NOT NULL,
  code_id                  INTEGER NOT NULL,
  invitee_email_hash       TEXT NOT NULL,
  invitee_email_encrypted  TEXT NOT NULL,
  store_order_id           INTEGER NOT NULL,
  order_amount_cents       INTEGER NOT NULL,
  status                   TEXT NOT NULL,   -- cooling | rewarded | capped | void
  void_reason              TEXT NOT NULL DEFAULT '',
  qualify_at               TEXT NOT NULL,   -- 发货时间 + 冷静期
  coupon_id                INTEGER,
  created_at               TEXT NOT NULL,
  updated_at               TEXT NOT NULL,
  UNIQUE (store_order_id),
  UNIQUE (agent_id, invitee_email_hash)
)

-- 邀请券：一张券一行
agent_referral_coupons (
  id                       INTEGER PRIMARY KEY,
  agent_id                 INTEGER NOT NULL,
  referral_id              INTEGER NOT NULL UNIQUE,
  code                     TEXT NOT NULL UNIQUE,
  owner_email_hash         TEXT NOT NULL,
  rewards_json             TEXT NOT NULL,   -- 发券时的 {plan_key: 立减分} 快照
  status                   TEXT NOT NULL,   -- unused | reserved | used | expired | revoked
  expires_at               TEXT NOT NULL,
  reserved_order_id        INTEGER,
  used_order_id            INTEGER,
  used_discount_cents      INTEGER,
  revoked_reason           TEXT NOT NULL DEFAULT '',
  revoked_by               INTEGER,
  created_at               TEXT NOT NULL,
  updated_at               TEXT NOT NULL
)
-- 索引：(agent_id, owner_email_hash, status)、(status, expires_at)
```

### 10.2 为什么不复用现有券表 `agent_store_coupons`

现有券是公共码，用「次数计数」管理；邀请券是一人一张、按商品定额、有状态流转（锁定、使用、退回、停用）、要知道是哪次邀请换来的。硬塞进去要加一堆只对一种券有意义的字段，代理的券列表也会被成千上万张个人券淹没。所以单独建表。结账时多一个分支，减免结果写进订单上已有的优惠字段。

### 10.3 现有表加字段

`store_orders`：

| 字段 | 说明 |
|---|---|
| `referral_code_id` | 这单是谁邀请来的（下单时记，发货时再判断是否有效） |
| `referral_coupon_id` | 这单用了哪张邀请券 |

减免金额沿用 `coupon_discount_cents`，`coupon_kind_snapshot` 写 `referral`，`coupon_code_snapshot` 写券码，账本、订单展示自动带上。`coupon_id`（手建券）和 `referral_coupon_id` 不能同时有值。

## 11. 什么时候做什么

| 时机 | 位置 | 做什么 |
|---|---|---|
| 打开店铺带 `?ref=` | 店铺页 | 浏览器按店铺记住邀请码 30 天，新的覆盖旧的 |
| 下单 | `store-orders.ts` | 记 `referral_code_id`；有邀请券就校验（§5.4）并锁券 |
| 付款成功 | 支付回调 | 券「已锁定 → 已使用」 |
| 关单 / 超时 / 退款 | 现有释放券的地方 | 券退回（§6） |
| 发货成功 | `fulfill-store-order.ts` 发货事务提交后 | 买家没有邀请码就生成；订单带邀请码就按 §4 判断，记邀请记录 |
| 每分钟 | `sync-scheduler.ts` | 冷静期到了的：再确认订单没退款 → 发券、发邮件；过期券改状态 |
| 好友订单退款 / 拒付 | 退款处理 | 邀请记录作废，没用的券停用 |

发券、记邀请都用唯一约束 + 条件更新保证不重复（定时任务和回调可能并发）。

### 11.1 接口

**店铺（买家，不登录）**

| 接口 | 用途 | 鉴权 |
|---|---|---|
| `GET /api/storefront/{slug}/referral/{code}` | 结账页校验手填的邀请码是不是这家店的，只回 `{ valid: true/false }` | 公开，按 IP 限流 |
| 现有下单接口 | 新增可选参数 `referralCode`；优惠券框里的码先按手建券查，查不到再按邀请券查 | 不变 |
| 现有查单接口（订单号 + 查询凭证） | 返回里加 `referral`：邀请码、链接、规则说明、成功人数、待到账张数；和 `coupons`：这个邮箱在这家店的邀请券 | 不变（本来就要完整订单号或邮件里的链接） |

**代理后台**

| 接口 | 用途 |
|---|---|
| `GET /api/agent/referral/settings` | 读设置和逐商品表（含售价、成本、最多能减） |
| `PUT /api/agent/referral/settings` | 保存设置和逐商品金额，超过「最多能减」返回 400 并指出是哪个商品 |
| `GET /api/agent/referral/summary?range=month\|all` | 汇总数字 |
| `GET /api/agent/referral/inviters?q=&page=` | 邀请人列表 |
| `GET /api/agent/referral/inviters/{codeId}` | 一个邀请人的邀请记录和券 |
| `POST /api/agent/referral/coupons/{id}/revoke` | 停用一张未使用的券，必填原因 |

**管理后台**

| 接口 | 用途 |
|---|---|
| `GET /api/admin/referral/summary` | 全站汇总、按代理列表、异常列表 |
| `GET /api/admin/referral/agents/{agentId}/inviters?q=&page=` | 同代理端明细 |
| `POST /api/admin/referral/agents/{agentId}/disable` | 替代理关闭活动 |
| `POST /api/admin/referral/coupons/{id}/revoke` | 停用一张券 |

所有写操作写审计日志：`agent.referral.settings`、`agent.referral.coupon.revoke`、`admin.referral.disable`、`admin.referral.coupon.revoke`。

### 11.2 时间口径

冷静期、有效期按精确时刻算（发货时间 + N×24 小时）；「每月上限」按北京时间自然月；界面一律显示北京时间。

### 12.3 验收用例

**邀请码**
1. 开启活动后，买家第一单发货成功 → 生成邀请码；再买一单，码不变。
2. 活动开启前发货的订单 → 不生成邀请码，查单页不显示邀请卡片。
3. 同一邮箱在两家店 → 两个不同的码。

**邀请记录**
4. 小李带小王的码首单发货 → 记一条「冷静期中」，7 天后发券给小王。
5. 小李以前在这家店付过款 → 不记录。
6. 小李用 `xiaowang+1@gmail.com`、`xiao.wang@gmail.com` 这类小王邮箱的变体 → 识别为自己邀请自己，不记录。
7. 带别家店的邀请码 → 忽略。
8. 订单低于最低金额、测试单、管理员补录单 → 不记录。
9. 小王本月已拿满 10 张 → 第 11 条记「超出上限」，不发券。
10. 冷静期内小李退款 → 记录作废，不发券。
11. 发券后、小王用券前小李退款 → 券停用。
12. 活动关闭后：冷静期中的照常发券；新订单带码不再记录。

**用券**
13. 小王用自己邮箱、买券上有金额的商品 → 按快照金额立减。
14. 别人拿到券码、用别的邮箱 → 拒绝「这张券只能用发券的邮箱下单」。
15. 买券上没金额的商品 → 拒绝。
16. 发券后代理降价，原金额会让这单亏本 → 自动减少到「最多能减」；减到 ≤ 0 就拒绝。
17. 一单 3 件 → 只减一次。
18. 同一张券并发下两单 → 只有一单锁券成功。
19. 锁券后订单超时关闭 → 券回到未使用。
20. 用券的单付款后退款 → 券在有效期内回到未使用，过期了变已过期。
21. 过期的券 → 拒绝。
22. 邀请券和手建券同时用 → 拒绝（只能一张）。

**设置和权限**
23. 某商品立减金额超过「最多能减」→ 保存失败并指出商品。
24. 一个商品都没填 → 不能开启。
25. 改设置后，已发的券面额不变。
26. 代理只能看、只能停用自己店的券；管理员能看全部，能关活动、停券，不能改面额。
27. 停用、关闭、改设置都有审计日志。

## 13. 已确认（2026-10-13）

| # | 问题 | 结论 |
|---|---|---|
| Q0 | 上线前的老买家要不要补邀请码 | **不补**，只有活动开启后发货的订单才生成（§3） |
| Q1 | 邀请券只做「按商品立减」 | **是**，不做折扣和满减 |
| Q2 | 面额只按「邀请人用券时买的商品」定，不看被邀请人买了什么 | **是** |
| Q3 | 冷静期 / 有效期默认 | **7 天 / 30 天**，代理可改 |
| Q4 | 管理员手动补录的订单算不算邀请 | **不算** |
| Q5 | 代理关闭活动后，已发的券还能用吗 | **能用到到期**；代理可以逐张停用 |
| Q6 | 用券那单退款后券退回吗 | **退回**（未过期时） |
| Q7 | 管理员能不能改代理的面额 | **不能**，只能关活动、停券 |
| — | 被邀请人这次拿不拿券 | **不拿**，只奖励邀请人 |
| — | 一单能用几张券 | **一张**，邀请券和手建券不能同时用 |
